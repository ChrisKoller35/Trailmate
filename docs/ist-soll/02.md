## Sicherheitsauffälligkeiten

1. **Backdoor "Dev-Vorschau (ohne Login)" im Login-Screen.** `app/(auth)/login.tsx:113-145` setzt per Knopfdruck eine Fake-Session und ein Fake-Profil (`is_premium: true`, `is_verified: true`) ohne Authentifizierung; nicht hinter `__DEV__` abgesichert (grep "__DEV__" in `login.tsx`: nicht gefunden). Supabase-Aufrufe scheitern zwar an RLS, aber alle Premium-Gates in der App sind damit umgehbar, und der Button würde in einen Release-Build gelangen.
2. **`users`-RLS gibt alle Spalten an alle Nutzer heraus.** `users_select` (`002_rls_policies.sql:519-532`) erlaubt jedem eingeloggten Nutzer `SELECT *` auf jedes öffentliche Profil, inklusive `email`, `push_token` und `notification_prefs`. Mehrere Screens laden tatsächlich `select('*')` fremder Nutzer (`app/followers.tsx:359-362`, `app/following.tsx:531-534`, `app/(onboarding)/follow-suggestions.tsx:60-62`). Die in Anhang A geforderte View `public_profiles` fehlt; auf Spaltenebene ist nichts eingeschränkt.
3. **Löschversuch fremder Zeilen per E-Mail.** `app/(onboarding)/home-region.tsx:79` führt `DELETE FROM users WHERE email = … AND id != auth.uid()` aus. RLS (`users_delete`, `002_rls_policies.sql:547-549`) blockiert das, der Code ist aber fehlleitend und sollte entfernt werden.
4. **Stille Fehlkonfiguration.** `lib/supabase.ts:5-6` fällt auf `https://placeholder.supabase.co` / `placeholder` zurück, statt bei fehlenden Umgebungsvariablen zu scheitern; `app/_layout.tsx:52-77` lässt die App nach 3 s auch ohne Supabase weiterlaufen.
5. **SecureStore-Adapter ohne Rückgabe der Promises** (`lib/supabase.ts:12-17`): Schreibfehler werden nie sichtbar; zusammen mit dem 2048-Byte-Limit kann die Session unbemerkt nicht gespeichert werden.
6. Positiv: `users_update`/`users_insert` sind korrekt auf `auth.uid()` eingeschränkt; `highlight_tours`, `follows`, `follow_requests` und `recordings` haben vollständige Policies.
